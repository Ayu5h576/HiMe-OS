## Problem Statement

Developers today live inside a fragmented toolchain: an IDE for code, a browser for GitHub, a chat app for AI assistance, and separate tools for CI/CD, issue tracking, and project planning. Context is lost at every boundary — the AI doesn't know what's in your repo, your repo doesn't know what you discussed with the AI, and your operating system treats GitHub as just another website.

HiMe OS was built to eliminate that fragmentation. The frontend MVP is complete, the backend foundation (Phases 1–12) is in place, and the Tool Calling Framework is ready — but there is **no native GitHub module**. GitHub is referenced only as a future automation target in the README; no OAuth flow, API client, webhooks, or UI exist.

Without native GitHub integration, HiMe OS cannot fulfill its core promise for developers: **One AI. Every Device. One Memory.** The AI cannot review your PRs, summarize your commits, or act on your repositories because it has no connection to them.

This issue proposes making GitHub a first-class native module — not a sidebar link, not a third-party plugin, but a deeply integrated subsystem that shares HiMe's memory, AI, automation, and permission model.

---

## Vision

> **One AI. Every Device. One Memory.**

GitHub integration aligns directly with the HiMe OS vision:

| Pillar | How GitHub Integration Delivers |
|--------|--------------------------------|
| **One AI** | HiMe AI gains full repository context — issues, PRs, commits, Actions — and can reason, act, and review on the developer's behalf |
| **Every Device** | Git operations and repo dashboards are accessible from any HiMe-connected device (desktop agent, mobile companion, voice) |
| **One Memory** | Repository activity, decisions, and patterns are persisted in HiMe's long-term memory (RAG pipeline), so the AI remembers *your* codebase across sessions |

Developers should be able to say *"Review this PR"* or *"What should I work on next?"* and receive answers grounded in live GitHub data and historical HiMe memory — without leaving the OS.

### OAuth Flow

```
User clicks "Connect GitHub"
  → GET /api/v1/github/auth/url
  → Redirect to github.com/login/oauth/authorize
  → User grants permissions
  → GitHub redirects to /api/v1/github/auth/callback?code=...
  → Backend exchanges code for access token
  → Token encrypted and stored in GitHubConnection
  → Redirect to HiMe OS /integrations/github?connected=true
```

Environment variables (add to `backend/src/config/env.ts` with Zod validation):

```
GITHUB_CLIENT_ID=
GITHUB_CLIENT_SECRET=
GITHUB_CALLBACK_URL=
GITHUB_WEBHOOK_SECRET=
GITHUB_TOKEN_ENCRYPTION_KEY=
```

### GitHub API Strategy

| Use Case | API | Rationale |
|----------|-----|-----------|
| List repos, issues, PRs, branches | REST v3 | Simple CRUD, well-documented |
| PR review with inline comments | GraphQL v4 | Batch mutations, review thread support |
| Repository search & analytics | GraphQL v4 | Complex queries, pagination |
| Webhook events | REST v3 webhooks API | Standard event delivery |
| Actions workflow runs | REST v3 | Actions API is REST-only |

Implement a unified `GitHubApiService` that abstracts REST/GraphQL selection and handles rate limiting (respect `X-RateLimit-*` headers, queue requests when near limit).

### Secure Token Storage

- Encrypt `accessToken` and `refreshToken` at rest using AES-256-GCM with `GITHUB_TOKEN_ENCRYPTION_KEY`
- Never expose tokens to frontend — all GitHub API calls are server-side
- Audit log for token access (future RBAC integration)
- Automatic token revocation on disconnect

### Permission Management

- Map GitHub OAuth scopes to HiMe permission tiers:

| Tier | Scopes | Capabilities |
|------|--------|-------------|
| Read | `read:user`, `repo:status`, `read:org` | Browse repos, view issues/PRs, analytics |
| Write | `repo` | Create issues, PRs, comments, merge |
| Admin | `admin:repo_hook`, `workflow` | Manage webhooks, re-run Actions |

- Scope upgrade flow: prompt user when an action requires higher permissions
- Enforce scope checks in service layer before every GitHub API call

### Webhooks

- Register webhooks on repo link for: `push`, `issues`, `pull_request`, `workflow_run`, `release`
- Verify signatures using `X-Hub-Signature-256` and `GITHUB_WEBHOOK_SECRET`
- Store events in `GitHubWebhookEvent`, process asynchronously
- Webhook processing triggers: memory re-index, activity feed update, automation rules, notifications

### Background Jobs

- **Repo sync job**: Refresh repo metadata, issue/PR counts (every 15 min for pinned repos)
- **Memory indexing job**: Index new commits, issues, PRs into pgvector (on webhook or scheduled)
- **Token refresh job**: Refresh expiring tokens before expiry
- **Analytics aggregation job**: Compute daily/weekly metrics (nightly)

Initial implementation: Fastify-compatible job runner (e.g., `bullmq` or in-process scheduler). Migrate to dedicated queue when scale demands.

## AI Features

HiMe AI interacts with GitHub through the Tool Calling Framework, RAG memory, and conversational interface.

### Example Interactions

| User Says | AI Action |
|-----------|-----------|
| *"Create an issue in hime-os titled Add GitHub integration"* | Calls `createGitHubIssue` → confirms → returns issue URL |
| *"Review this PR"* | Fetches PR diff → runs AI review → posts review comment → summarizes findings |
| *"Summarize today's commits across my repos"* | Calls `summarizeGitHubActivity` with date filter → returns formatted summary |
| *"Push current branch"* | Delegates to Desktop Agent (Phase 15) → stages, commits with AI message, pushes |
| *"What should I work on next?"* | Queries open issues + PR reviews needed + failed Actions + HiMe Tasks → prioritized recommendation |
| *"Show me all PRs waiting for my review"* | Calls `getGitHubPullRequests` filtered by review-requested → renders list |
| *"Why did the CI fail on PR #23?"* | Fetches Actions run logs → AI summarizes failure root cause |
| *"Link the hime-os repo to my Backend project"* | Calls repo link API → syncs issues as tasks |
| *"What did we decide about the auth architecture?"* | RAG query against repository memory + conversation history |

### AI PR Review Pipeline

```
1. Fetch PR diff (GraphQL)
2. Load repository memory (coding patterns, past review feedback)
3. Run AI analysis:
   - Code quality & readability
   - Security concerns (hardcoded secrets, injection risks)
   - Test coverage gaps
   - Consistency with project conventions
4. Generate inline review comments on specific lines
5. Post summary review (approve / request changes / comment)
6. Store review insights in HiMe Memory for future reviews
```

### Context Injection

When a user is viewing a GitHub repo/PR/issue, the AI Context Builder automatically injects:
- Repository metadata and linked HiMe Project
- Recent commits and open PRs/issues
- Relevant memories from RAG pipeline
- Current branch and file context (when browsing code)
